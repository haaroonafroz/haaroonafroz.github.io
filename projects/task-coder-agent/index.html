PERSONAL PROJECT · AGENT SYSTEMS · SOFTWARE ENGINEERING

Missions An AI coding harness for building, fixing and reviewing software.

I built Missions to bring structure to how coding agents work. Start a new project or attach an existing repository, ask questions, plan changes, and move into implementation. Specialized roles handle planning, focused fixes, code review and validation, while the runtime manages tool permissions, recovery and session state.

01 · USING MISSIONS

Understand the code. Plan the change. Build it.

The chat mode sets what the harness can do. In Build mode, a separate routing decision selects a full Mission, a focused Hotfix or Code Review.

ASK

Explore a codebase.

Inspect files, search code and ask questions with read-only tools. Ask mode cannot edit files, execute commands or install dependencies. Preferences and constraints carry into later work through a compact conversation brief.

PLAN

Agree on the approach.

The Orchestrator drafts milestones and acceptance criteria, with optional read-only exploration. Adjust the plan before approving it for execution. Implementation workers start after approval.

BUILD

Choose the right workflow.

Execute a prepared plan or route a new request. Larger changes use the Mission pipeline, localized defects can use a Hotfix, and review requests produce findings with a choice of follow-up actions.

Workspaces can be managed by Missions or attached from an existing folder, with read/write or read-only access. The web interface streams agent turns, tool activity, milestones and token usage so the work stays inspectable.

02 · THE DESIGN QUESTION

How much capability can better system design unlock?

Missions began with resource-constrained local models and a question: can a carefully engineered runtime make them more useful on non-trivial coding tasks? That motivation now informs a harness that also supports cloud models and existing repositories.

01

Context is finite.

Planning, implementation and debugging compete for attention. Focused roles, small tool surfaces and compact handoffs keep each model call anchored to a specific job.

02

Failures have different causes.

A broken implementation, a flawed plan and a missing test toolchain need different responses. The runtime distinguishes repair, replanning and work that could not be verified.

03

Hardware shapes the architecture.

Agent roles execute serially, with one active LLM role at a time. This limits concurrent inference memory pressure on constrained local GPUs.

03 · ARCHITECTURE

Route work by scope, then validate the changes.

Triage selects an execution route using the request and workspace context. Explicit review requests and new empty workspaces also have deterministic routing. Focused fixes can escalate when a larger plan is needed.

04 · REVIEW AND FIX

Turn findings into a controlled follow-up.

The reviewer returns structured findings with affected files, evidence, confidence and criteria for a fix. High-confidence bugs and blockers can become focused fix packets; the default interactive flow pauses for a user decision.

01

Review without editing.

The reviewer cannot patch files, install dependencies or commit. A read-only workspace returns the report without applying changes. Review checks remain subject to execution policy.

02

Verify the focused fix.

After implementation, FixVerifier combines targeted deterministic checks with a focused model verdict against the original fix criteria. Rework and escalation retain the findings as context.

03

Make uncertainty visible.

If test infrastructure or required checks are unavailable, the outcome can be UNVERIFIED. The user can run a smoke check, set up the environment or choose another follow-up.

05 · CORE SYSTEM IDEAS

The runtime owns the development loop.

ACCEPTANCE-FIRST

Define what success looks like.

Milestones carry acceptance criteria and validation profiles. The Validator compiles executable checks and inspects actual changes alongside the implementation report.

DETERMINISTIC CHECKS

Enforce structure in code.

Plan linting, tool argument schemas, write policies and structural validation handle checks that can be expressed programmatically.

SCOPED EDITING

Bound each implementation step.

File-edit tools enforce milestone scope. Diff-first editing encourages targeted patches, and workers can request additional scope when the packet omits a necessary file.

PATCH-BASED REPLANNING

Preserve completed work.

Planning failures produce validated patch operations over milestones. Completed milestones remain immutable; replan budgets and repeated failure signatures stop circular recovery.

SESSION MEMORY

Carry state across retries.

A durable JSON store records milestone completion and validation failures. Plans, handoffs and event logs preserve context for repair and resuming interrupted runs.

TOOL DISCOVERY

Retrieve specialized capabilities.

A stable core tool surface supports everyday work. Qdrant hybrid retrieval adds relevant specialized tools, while the runtime enforces the active tool set and argument contracts.

06 · MY ENGINEERING WORK

Building the AI workflow and the application around it.

I designed and implemented the agent roles, routing and recovery logic alongside the Python runtime, FastAPI backend and React/TypeScript interface. Packaging, configuration, workspace attachment and observability make that architecture usable as a development tool.

01

Serial agent execution

Work within the hardware budget.

Each role gets a focused turn, keeping concurrent inference memory usage predictable on local hardware.

02

Separate inference from the harness

Connect the model provider you choose.

Provider adapters support local OpenAI-compatible endpoints and cloud APIs. The harness manages the workflow; model serving remains external.

03

JSON configuration and secrets

Make installation and settings explicit.

The Settings UI and settings.json configure providers, agent roles and integrations. API keys live separately in secrets.json, which should remain outside version control.

04

Inspectable execution

Expose what the agents actually did.

Streaming events, tool diagnostics, milestone status and token accounting connect the control interface to the runtime. Optional Phoenix tracing supports deeper inspection.

07 · GET STARTED

Try it on a small project.

Use native installation to attach host repositories directly, or Docker for managed workspaces and explicitly mounted projects. Connect a model endpoint or cloud provider in Settings.

NATIVE INSTALL

Work with local repositories.

Linux is the primary target. Install Python 3.10+, Node.js 18+ and Git, then run:

git clone https://github.com/haaroonafroz/task-coder-agent.git missions
cd missions
bash scripts/install.sh
source .venv/bin/activate
missions doctor
missions serve

Open http://127.0.0.1:8088 and use the setup wizard. Create a workspace or attach an existing folder with the access mode you need.

DOCKER INSTALL

Run the harness in a container.

With Docker Compose installed, clone the repository and start the app:

git clone https://github.com/haaroonafroz/task-coder-agent.git missions
cd missions
docker compose up --build

Open http://localhost:8088. To attach a host project, add a bind mount to Compose and enter its container path in the UI, for example /host-projects/my-app.

The image runs the harness. Local model serving stays on the host or another service; cloud providers use your API key.

Provider and configuration guide ↗ · Supported endpoints include llama.cpp, Ollama, LM Studio and vLLM, alongside cloud providers. Configure non-secret settings in settings.json and provider keys in secrets.json.

08 · CURRENT STATUS

An evolving proof of concept.

Missions implements these workflows, but model behaviour, repository complexity and available checks still determine outcomes. This case study describes the design and implementation; comparative reliability and productivity measurements remain future work.

EVALUATION

Measure representative tasks.

A useful next evaluation would compare completion rate, regressions, token cost and recovery behaviour across greenfield builds, fixes and reviews on existing repositories.

EXECUTION BOUNDARIES

Understand the installation.

Native Linux execution can use bubblewrap; without it, command policy provides the checks. The Docker image uses the native executor, and attached host paths must be explicitly mounted.

FEEDBACK

Learn from real workflows.

I am interested in where routing, planning, review quality and setup friction need improvement. A small reproducible example is especially useful for shaping the next iteration.
